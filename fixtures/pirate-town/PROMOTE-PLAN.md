queries, and the `data/` index is the universal reference that `catalogue.reference.ingest` compiles (DESIGN §2.2).

## (b) V6 after promotion (`src/drift.ts`)

Today `inspectDrift` walks `fixtures/<name>/`, hashes the files each manifest lists, and checks `derived_from` only
in `fixtures/<name>/records`. A record moved to `data/` would leave V6 without any test failing. The fix:

1. **Hash table over all manifests.** Build one map from source path to sha256 out of every `fixtures/*/manifest.json`.
   Paths are relative to the repo root (`resolve(repoRoot, row.path)`), so a `derived_from.file` means the same thing
   from `data/` as from `fixtures/`. If two manifests list the same path with different sha256 values, both
   manifests fail with `listed by fixtures/<a> and fixtures/<b> with different sha256`.
2. **Fixture records keep their own manifest.** `fixtures/<name>/records/**` records are still checked against
   their own fixture's manifest, as now.
3. **`data/` records use the shared map.** Every `data/**/*.json` file except `data/aliases.json` is checked:
   - It needs a `derived_from` array. An empty array is a native record: it is counted and passes.
   - Each entry's `file` must appear in some manifest (`<file>: not in any fixture manifest; re-ingest record`).
   - Its `sha256` must equal that manifest's hash (`<file>: sha256 differs from manifest; re-ingest record`).
4. **`--update` is unchanged.** It refreshes manifest hashes only and never touches a record, wherever the record
   is. A changed source then fails its `data/` records until they are re-ingested.
5. **The summary line keeps its format.** `records` counts fixture and `data/` records together. After the move,
   `fixture-drift.ts` reports 7 files, 664 records, 0 failures.

So a fixture's manifest must outlive its promotion: deleting `fixtures/pirate-town/manifest.json` fails every
promoted record that derives from it. That failure is intended.

## (c) What `check.ts`, `load.ts` and the window query need

- **`src/load.ts`: no change.** It already loads every `.json` under `data/` except `data/aliases.json`, plus
  `fixtures/*/records/**`. The promoted records and the game-scoped record that stays are loaded together.
  Because of this, no other `.json` file may sit in `data/`: it would be loaded as a record and fail V1 (see (d)).
- **`src/check.ts`: three V1 rules, all passing today.**
  1. A file under `data/` (other than `data/aliases.json`) must be at `data/<kind>/<slug>.json`, where `<kind>` is
     the record's `kind`: `directory must be data/<kind>/`. Today only the file name is checked.
  2. A record under `data/` must have `scope: universal`: `game scope stays under fixtures/, not data/`.
  3. A `universal` record may not refer to a `game:`-scoped record in `sources`, `relations[].to` or `.sources`,
     `place`, `culture`, `names[].region` or `.period`: `universal record references game-scoped <id>`. The fixture
     has none today. The rule keeps a default window from depending on fiction it filters out.

  A record copied but not deleted is already caught as `duplicate id`.
- **`src/window.ts`: no change.** `createWindowQuery` reads `records` and `aliases`, not file paths, and the
  `canonical` entry it returns carries no path. Byte-identical records therefore give byte-identical bundles. The
  move unit's gate proves identity by requiring 663 pure renames (`R100`). The game-scoped record is still loaded,
  because `load.ts` still reads `fixtures/*/records`, and the default scope set (`universal`) still leaves it out.
  It has no attestation or observation (DESIGN-V4 exception (f)), so no window returns it under any scope, before
  or after the move.

## (d) `data/sources.json` and the fixture's source records

DESIGN §2.3 names `data/sources.json` ("source keys: author, title, year, what it gives, rights"). As built, a
source is a record with `kind: source`, id `catalogue/source.<slug>` (key `TWN-NAS` → slug `twn-nas`). Its `source`
block holds `key`, `title` (author and year inside it), `gives`, `rights` and `url`, and its `derived_from` points
to its SOURCES.md or RESEARCH.md row. Every citation is a `ref` that V1 resolves.

**Ruling:** `data/sources.json` is not written. The source records in `data/source/<slug>.json` are the source
store. A second list would duplicate them, and `load.ts` would load it as a malformed record. If a key list is ever
needed, it is derived when building `dist/catalogue.json`, never kept by hand. The move unit removes the scaffold's
`data/sources/.gitkeep`, so that `data/sources/` and `data/source/` do not sit side by side. It also replaces the
§2.3 sentence (text in unit P3).
